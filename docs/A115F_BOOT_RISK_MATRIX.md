# A115F One UI 7 boot-port risk & test matrix

**Scope:** experimental ZineROM One UI 7 donor port for Galaxy A11 `SM-A115F` only. This is a test plan and a set of guardrails—not a claim that the ROM has been built or that every future defect is fixed.

## Current evidence and limits

- The supplied logs identify `SM-A115F`, bootloader `A115FXXS6CWK2` (Binary 6), and device sales code `INS`. The first CI attempt failed because the importer hardcoded the INS FUS region. A metadata-only Samloader-rs 2.2.0 query for `SM-A115F/MWD` returned the exact pinned AP/CSC/CP/BL tuple; INS failed to parse FUS history. CI run `40120489519` later downloaded the pinned MWD package, validated its five Odin payloads and embedded MD5 trailers, extracted target files, and passed the firmware-layout gate. MWD is only a source lookup; the phone sales code is not changed and the MWD CSC tar is not flashed.
- Build run `40120489519` then failed inside the shared `stock_blobs` patch because the target importer omitted `system.img` while `unica/patches/stock_blobs/customize.sh` tried to copy `system/saiv` from that target tree. The fix now includes target `system` as a source-only extraction, validates it and its fs metadata, and skips SAIV replacement safely if the target tree is absent. This fix still needs a new CI run. The current local checkout contains no extracted firmware or ROM ZIP; Actions scratch data is ephemeral.
- The boot log records an unsuccessful logical-partition update for `system_ext`, then continues into second-stage init. Later, `vold`/KeyStorage attempts file-based encryption, `enablefilecrypto` returns `Status(-8, EX_SERVICE_SPECIFIC)`, the property `security.fbe.fail_cause` is set to `K00R`, and init reboots to recovery. Neither `K00R` nor the `system_ext` message alone establishes the root cause or a causal link.
- Target config says `TARGET_HAS_SYSTEM_EXT=false`; build code intends to merge donor `system_ext` under `system`, not flash a separate logical `system_ext`. This must still be confirmed against the exact target fstab and `super` metadata.
- The A115F tree has no device-specific fstab/kernel-source patch in the current scaffold. The pipeline is intended to take vendor and kernel images from target firmware, but no such target images are currently available locally. No custom vendor/kernel has been built.
- A ZIP validator, test fixtures, firmware-cache protections, and CI gates have been added. The previous CI run proves firmware intake/layout only; it produced no ZIP and cannot prove Android boots.

## Severity key

- **P0 — boot-blocking / safety gate:** do not flash or publish as boot-ready until resolved or explicitly characterized.
- **P1 — likely boot or first-boot failure:** requires targeted evidence and a fix/test before claiming boot animation.
- **P2 — post-animation functionality:** not required to reach animation, but must be tracked before calling the port complete.

## Boot-stage triage: collect evidence, do not guess

| Last visible stage | First evidence to collect | Primary branches to investigate |
|---|---|---|
| Samsung/OEM logo, no ADB | `/sys/fs/pstore/*`, `last_kmsg`, recovery log, target boot/vbmeta/DTBO identity | AVB, boot image, DTB/DTBO, kernel panic/watchdog |
| Android init starts then reboots | Full kernel log, first/second-stage init, fs_mgr, `lpdump`, mount table, exact target fstab | `super`/group, system_ext layout, fstab source/filesystem, init service failure |
| `/data`/vold stage then reboot | `vold`, KeyStorage, KeyMint/Keymaster, QSEE/TEE, fscrypt, `/metadata`, encryption flags | FBE configuration/service compatibility; `K00R` stays an unexplained observed value unless proven |
| Boot animation appears but stays there | `adb logcat -b all`, `sys.boot_completed`, SystemServer crash/restart, SurfaceFlinger/HWC logs | framework/vendor compatibility, graphics, SystemServer, storage unlock |
| Setup/home appears | radio, Wi-Fi, camera, audio, sensors, fingerprint and suspend tests | Post-animation functionality; this is separate from merely reaching animation |

## Required gates before calling it “booted”

- [ ] Exact A115F target firmware/CSC and donor firmware are pinned and archive hashes recorded.
- [ ] Extracted target `super` inventory matches config; every target-side partition appears in both the work directory and final ZIP, with target VINTF and Keymaster/KeyMint evidence.
- [ ] Target `super`, group, fstab, `system_ext`, boot/DTBO and AVB assumptions match the same verified A115F firmware.
- [ ] Unit tests pass; the full build completes; final ZIP passes `scripts/validate_a115f_zip.py`; ZIP SHA-256 is recorded.
- [ ] Recovery identity and by-name paths are checked on an actual SM-A115F; stock restore package and Download Mode are ready.
- [ ] A first boot reaches animation without repeated reboot; logs show no fatal init/FBE cause. Record this separately from `sys.boot_completed`/Setup Wizard.
- [ ] A second reboot is tested without another format to catch FBE persistence issues.
- [ ] Capture each failure before changing code; change one evidence-backed cause at a time.

## Fixes made in this worktree

- Fixed stale ZIP member-list reuse after interrupted builds.
- Fixed firmware extraction reuse: exact version marker required; partial/stale output is not reused; required partitions/kernel images must exist before the atomic `.extracted` marker is written.
- Added archive path/duplicate/symlink/size checks, verified required Odin payloads, and introduced configurable disk-space guards before download/extraction.
- Changed SignApk build to use a disposable copy so it does not leave transformed symlinks in the source submodule.
- Replaced contradictory generic README wipe/manual-image steps with a target-specific A115F reference.
- Added archive, firmware-layout, ZIP, and stock-blob regression tests with 46 tests total (14 archive intake, 14 firmware layout, 16 flashable ZIP safety, 2 stock-blob behavior). Local A115F package generation and CI run ZIP validation; CI also runs tests before the build and validates the ZIP before private artifact upload.
- The firmware-layout validator checks the configured exact A115F version, physical super size/group, source-only target `system` and its metadata, every hardware-side logical partition, boot/DTBO, VINTF security HAL, executable init service and `/data` fileencryption flags. The ZIP validator checks target partition payloads, dynamic operations, exactly one leading `remove_all_groups`, and matching updater writes.
- Pinned every GitHub Action to a full commit SHA, moved `setup-java` to v5, retained `gh` in the runner cleanup step, and disabled checkout credential persistence.

## Explicit non-claims

No ROM ZIP was built; the device was not flashed; there is no boot-animation success result. CI run `40120489519` downloaded and verified the exact A115F MWD archive and passed the target vendor/FBE/layout gate, then failed because the optimized importer omitted target `system` while the stock-blob patch required it. The current changes extract and validate that source-only partition and make SAIV replacement conditional; they pass 46 local unit tests but still need a fresh workflow run. The new gates cannot prove Android boots. The matrix is comprehensive for the observed boot path, not a guarantee against every possible defect. “All bugs” can only be approached through repeated build → device test → log-driven fix cycles.
